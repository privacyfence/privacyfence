Grist connector: the steps only you can do

Do the two Before implementation tasks before you run /implement; the QA-recording phase needs them. Do the After implementation checks once the feature PR is up, and tick them in the PR. Your ticks here are saved in this browser only.

Part 1

Before implementation

1. Create a Grist QA account, seed document and API key

mb1-grist-qa-accountabout 15 min

Phase p12 records live fixtures from this document with this account's API key. Use an account that holds nothing real. If you already did an earlier version of this task, only steps 5 and 8–9 may be new.

The key acts as the QA account, with access to every document it can open. Never paste it into a chat, the plan, a PR, an issue or a GitHub secret. Its only other copy is the runner file in task 2 (ADR 0019). If you already registered an OAuth app on this account, keep it: task 3 uses it.

Done when: the seed document has QaSeed with two [QATEST] rows and an empty QaLifecycle, the contrast document exists, and the QA account's API key is in your password manager.

2. Put the API key and the seed ids on the QA runner

mb2-runner-qa-stateabout 5 min

Phase p12 dispatches qa-record-fixture.yml, which copies ~/privacyfence/ from the runner (labelled privacyfence-test) into its checkout (connector-qa.md, Persistent QA state). No bundle change is needed: without a Grist OAuth app in the bundle, Grist uses the API key.

Done when: on the runner, ~/privacyfence/credentials/grist_token.json exists with mode 600 and holds auth "api_key", server_url and api_key; qa_environment.yaml has a grist section with doc_id, table_id and lifecycle_table_id; and the runner's bundle carries no Grist OAuth app. Then tell the /implement session that both before-steps are done.

Part 2

After implementation

3. Connect with an API key, drive every Grist tool, then sign in with OAuth

ma1-local-mode-checkabout 40 min

Proves the key form, what the approval cards show and that real writes land, and gives the OAuth sign-in its first run against real Grist. The live check uses only the API key.

Report back: tick the item in the PR and paste one line, for example ma1 local mode: PASS (API key: wrong-key error, review card, 4 write cards, rule; OAuth: sign-in, listing allowed/refused, revoke), or FAIL at step N: what you saw.

4. Connect Grist on /connect in an org-mode test deployment

ma2-org-mode-checkabout 25 min · only if you run one

Proves the bundle's grist section, the per-person key form, the org redirect and the OAuth sign-in. No CI job runs an org deployment against Grist.

Report back: tick the item in the PR and paste ma2 org mode: PASS (key and OAuth), FAIL at step N: what you saw, or ma2: skipped, no org-mode test deployment.
