Grist connector: the steps only you can do

Do the two Before implementation tasks before you run /implement; the QA-recording phase needs them. Do the After implementation checks once the feature PR is up, and tick them in the PR. Your ticks here are saved in this browser only.

Part 1

Before implementation

1. Create a Grist QA account, seed document and API key

mb1-grist-qa-accountabout 15 min

Phase p9 records live fixtures from this document. Use an account that holds nothing real.

The key acts as this account with access to every document it can open. Never paste it into a chat, the plan, a PR, an issue or a GitHub secret. Its only other copy is the runner file in task 2 (ADR 0019).

Done when: a Grist document named "PrivacyFence QA [QATEST]" has a table QaSeed (columns Name, Note) with two [QATEST] rows, a second document exists as a contrast case, and an API key for this account exists (kept only in your password manager).

2. Put the Grist key and seed ids on the self-hosted QA runner

mb2-runner-qa-stateabout 10 min

Phase p9 dispatches qa-record-fixture.yml, which copies ~/privacyfence/ from the runner (labelled privacyfence-test) into its checkout. See connector-qa.md, Persistent QA state.

Done when: on the runner, ~/privacyfence/credentials/grist_token.json exists with mode 600 and the keys server_url and api_key, and ~/privacyfence/tests/fixtures/qa_environment.yaml has a grist section with doc_id, table_id and seed_record_name. Then tell the /implement session that both before-steps are done.

Part 2

After implementation

3. Connect Grist in Settings and drive every Grist tool from an AI client

ma1-local-mode-checkabout 30 min

Proves the Settings form, what the approval cards show and that real writes land, which unit tests and the recorder cannot show.

Report back: tick the item in the PR and paste one line, for example ma1 local mode: PASS (wrong-key error, review card, 4 write cards, rule auto-accepts read), or FAIL at step N: what you saw.

4. Connect Grist on /connect in an org-mode test deployment

ma2-org-mode-checkabout 20 min · only if you run one

Proves the bundle's grist section, the per-person key form and that the pinned server is used. No CI job runs an org deployment against Grist.

Report back: tick the item in the PR and paste ma2 org mode: PASS, FAIL at step N: what you saw, or ma2: skipped, no org-mode test deployment.
