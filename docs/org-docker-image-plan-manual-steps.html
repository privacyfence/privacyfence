Plan · org-docker-image

Manual checks for the organization Docker image

These are the only steps in this plan that need you: one settings check before implementation starts, and two checks after the work is done. Every phase builds and tests the image itself. Your ticks are saved in this browser only.

Before implementation

mb1-allow-attest-action

Allow the provenance action, if Actions use an allowlist

about 3 minNeeds the repository admin role
  1. Open the repository's Actions settings (Settings, Actions, General).
  2. Under Actions permissions, look at which option is selected. If it's Allow all actions and reusable workflows, you're done: skip to the last step.
  3. If it's Allow privacyfence, and select non-privacyfence, actions and reusable workflows, check whether Allow actions created by GitHub is ticked. If not, add actions/attest-build-provenance@* on its own line in the Allow specified actions and reusable workflows box. Click Save.
  4. Done when the page shows all actions allowed, actions created by GitHub allowed, or actions/attest-build-provenance@* in the list. Tell the /implement session it's done.

Why: a workflow that uses an action outside the allowlist fails at startup with no jobs and no logs. The new publish workflow can't run before a stable tag, so nothing earlier would show the failure.

After implementation

ma1-real-server-compose

Run the pre-flight image on a real server

about 45 minNeeds an amd64 Linux server with Docker Engine 24+ and Compose 2.24+, a public hostname with DNS, ports 80 and 443 open, and a test client in your identity provider
  1. Open the Build & Release runs for feature/org-docker-image and pick the newest green run (the PR description links it). You should see the jobs build-org-image (amd64) and build-org-image (arm64) with green ticks.
  2. At the bottom of the run summary, under Artifacts, download org-image-amd64. It's a zip of about 150 MB. Copy it to the server, for example with scp.
  3. On the server, load the image and give it the name the Compose file expects: 
    unzip org-image-amd64.zip
gunzip -c privacyfence-org-amd64.tar.gz | docker load
docker tag privacyfence-org:ci-amd64 ghcr.io/privacyfence/privacyfence-org:preflight
    You should see Loaded image: privacyfence-org:ci-amd64.
  4. Make the deploy directory and fetch the two deploy files from the feature branch: 
    sudo mkdir -p /opt/privacyfence-org && cd /opt/privacyfence-org
sudo curl -fsSLO https://raw.githubusercontent.com/privacyfence/privacyfence/feature/org-docker-image/deploy/docker/compose.yaml
sudo curl -fsSLO https://raw.githubusercontent.com/privacyfence/privacyfence/feature/org-docker-image/deploy/docker/Caddyfile
  5. Create /opt/privacyfence-org/.env with two lines: PF_HOSTNAME= followed by your test hostname, and PRIVACYFENCE_IMAGE_TAG=preflight.
  6. Register the three redirect URIs for your hostname with the test identity provider, as the guide's Identity provider section describes. Then build and sign a bundle as Build the bundle describes, with --server-bind-host 0.0.0.0 --server-trusted-proxy 172.30.87.2. The client secret goes into the bundle on your own machine. Never paste it into the PR or a chat.
  7. Install the bundle into the data volume, from /opt/privacyfence-org: 
    docker compose run --rm -T --entrypoint sh privacyfence -c 'umask 077 && cat > /var/lib/privacyfence-org/.privacyfence/org/org_config.json' < org_config.json
  8. Start it with docker compose up -d, then run docker compose logs privacyfence | grep "Org mode active". You should see one line naming https://<your hostname>/mcp.
  9. In a browser, open https://<your hostname>/login and sign in. You should land on the approvals page, served with a valid certificate (Caddy obtained it).
  10. On /connect, connect one service the bundle offers. Its row should show it as connected.
  11. Add the server to an AI client, for example claude mcp add --transport http pf https://<your hostname>/mcp in Claude Code. Ask it to read something from that service, and approve the request in the browser. The client should get the result.
  12. Run docker compose restart privacyfence, sign in again, and open /settings. The audit entry for that approval should still be listed, and the service should still be connected.
  13. Clean up with docker compose down -v. This deletes the test data volume as well.

Report back as a comment on the PR, then tick its box: ma1 real-server compose: PASS or ma1 real-server compose: FAIL, step N: what you saw.

ma2-first-release-ghcr

At the first stable release after merge: make the package public and verify it

about 10 minNeeds the organization owner role on GitHub, and the gh CLI on any machine
  1. Before you cut the release, open the organization's package settings. Under Package creation, make sure Public is allowed.
  2. Cut the stable release as usual (/cut-release). Then open the Publish org Docker image runs. The run for the tag should be green, with a summary naming the tags and digest.
  3. Open the privacyfence-org package, then Package settings. Under Danger Zone, choose Change visibility, then Public, and type the package name to confirm. On the same page, check that Manage Actions access lists the privacyfence repository.
  4. On a machine that isn't logged in to ghcr.io, run docker logout ghcr.io; docker pull ghcr.io/privacyfence/privacyfence-org:X.Y.Z, with the version you released. The pull should succeed without credentials.
  5. Run gh attestation verify oci://ghcr.io/privacyfence/privacyfence-org:X.Y.Z --owner privacyfence. It should end with Verification succeeded!.
  6. Run docker buildx imagetools inspect ghcr.io/privacyfence/privacyfence-org:latest. It should list both linux/amd64 and linux/arm64.

Report back as a comment on the merged PR (or the release): ma2 GHCR first release X.Y.Z: PASS, or the step that failed and its output.
