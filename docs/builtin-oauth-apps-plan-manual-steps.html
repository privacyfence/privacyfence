Built-in Apps Setup

The steps only you can do for the builtin-oauth-apps plan. The part before implementation must be done before /implement starts. The part after implementation is done once the feature branch is complete, before its pull request merges. Never paste a secret into a chat, an issue or this page. Each secret has one named home, given in its step.

Before implementation

1. Register the seven PrivacyFence-owned OAuth apps and store them as repository secrets

mb1-register-builtin-appsabout 2–3 hours

Register each app under a PrivacyFence account, not a personal one or a customer's. Each app's name is PrivacyFence, so that is what people see on the consent screen. You need a public privacy policy URL (https://privacyfence.eu/privacy/) and a homepage (https://privacyfence.eu). For the scopes or permissions, follow the repo's own setup guide for each provider; the redirects below replace the ones those guides list.

  1. Google project. Create a project named privacyfence-builtin at console.cloud.google.com/projectcreate. Then enable the Gmail, Drive, Calendar, People, Tasks and Apps Script APIs in its API library. The list and scopes are in google-cloud-setup.md.
  2. Google branding. In Google Auth Platform → Branding, set the app name to PrivacyFence and add the homepage and privacy policy URLs. In Audience, choose External and In production. In Data Access, add the scopes from google-cloud-setup.md.
  3. Google clients. At Clients → Create client, create a Desktop app named "PrivacyFence desktop". Then create a Web application named "PrivacyFence relay" with the six redirect URIs from the table. Copy each ID and secret straight into the GitHub secrets in the last step of this section. You should see two clients listed.
  4. Slack. At api.slack.com/apps → Create New App, choose "From scratch" in your PrivacyFence workspace. Under OAuth & Permissions, add both redirect URLs and the user token scopes from slack-setup.md. Under Manage Distribution, complete the checklist and choose Activate Public Distribution. The client ID and secret are under Basic Information → App Credentials.
  5. Salesforce. In a Developer Edition org you control (sign up at developer.salesforce.com/signup if you have none), open Setup → App Manager → New Connected App. Enable OAuth, add both callback URLs on separate lines, and add the scopes from salesforce-setup.md. Turn PKCE on. The consumer key and secret are under Manage Consumer Details.
  6. Atlassian, two apps. At developer.atlassian.com/console/myapps, choose Create → OAuth 2.0 integration twice: "PrivacyFence" with the local callback, and "PrivacyFence (organization servers)" with the relay callback. Add the Jira and Confluence permissions from atlassian-setup.md, including the Assets scope. Under Distribution, set each app to Sharing and fill in the vendor and privacy details.
  7. Miro. At miro.com/app/settings/user-profile/apps, create an app named PrivacyFence and tick Expire user authorization token. This cannot be changed later. Add both redirect URIs and the permissions boards:read and boards:write. Then make the app available to other users (Distribute / public app), as described in miro-setup.md.
  8. Store the 14 secrets. At Settings → Secrets and variables → Actions → New repository secret, add each name from the table's last column, one per ID and one per secret. Paste each value directly from the provider console into GitHub's form. They are repository secrets, not environment secrets, because build.yml and publish-pypi.yml read them that way.

Done when: the repository's Actions secrets list shows all 14 names: PF_APP_GOOGLE_DESKTOP_CLIENT_ID/_SECRET, PF_APP_GOOGLE_WEB_CLIENT_ID/_SECRET, PF_APP_SLACK_CLIENT_ID/_SECRET, PF_APP_SALESFORCE_CLIENT_ID/_SECRET, PF_APP_ATLASSIAN_LOCAL_CLIENT_ID/_SECRET, PF_APP_ATLASSIAN_RELAY_CLIENT_ID/_SECRET, PF_APP_MIRO_CLIENT_ID/_SECRET.

2. Create the Cloudflare token and the GitHub environment for the relay Worker

mb2-relay-worker-cloudflareabout 20 minutes
  1. In Cloudflare, open the account's account API tokens page and create a token named privacyfence-oauth-relay-deploy. Give it Account: Workers Scripts Edit, and Zone: Workers Routes Edit and Zone Read. Scope the zone resources to privacyfence.eu and leave the expiry empty. This is the same shape as the download Worker's token in downloads-and-release-kpi.md, without the D1 and R2 permissions.
  2. Verify it in your own terminal. Read the token from your password manager into an environment variable; don't type it into a chat. Run:
    curl -s -H "Authorization: Bearer $CF_TOKEN" \
  https://api.cloudflare.com/client/v4/accounts/326657b4f70af041996d60fd6b8f83fa/tokens/verify
    You should see "status": "active".
  3. Create a GitHub environment named oauth-relay-worker at Settings → Environments → New environment. Under Deployment branches, allow only main.
  4. In that environment, add three secrets:
    • CF_OAUTH_RELAY_WORKER_API_TOKEN: the token.
    • CF_OAUTH_RELAY_WORKER_ACCOUNT_ID: 326657b4f70af041996d60fd6b8f83fa.
    • CF_OAUTH_RELAY_REVOKE_TOKEN: a new random value made with openssl rand -base64 32 in your terminal. Keep a copy in your password manager; you need it to revoke a server.

Done when: the oauth-relay-worker environment holds the three secrets, and the curl above reports the token active.

3. Optional: submit the Google app for verification

mb3-google-verification30 minutes now, then weeks of waiting

Nothing in the plan waits for this. Until Google verifies the app, people see an "unverified app" screen, and the app is capped at 100 users in total. Gmail and Drive scopes are restricted, so verification includes an annual security assessment by a third party.

  1. Open Google Auth Platform → Verification Center for privacyfence-builtin. Choose Prepare for verification, and give the scope justifications and the demo video Google asks for.
  2. Submit it, or decide to defer it and note that in the tracking issue.

Done when: the Verification Center shows the submission, or you decided to defer it.

After implementation

4. Sign in with the built-in apps on a desktop install

ma1-desktop-builtin-signinabout 45 minutes
  1. Get an installer from the feature branch. Open Actions → build.yml, choose Run workflow, and pick branch feature/builtin-oauth-apps, or ask the orchestrator session to dispatch it. Download your platform's installer from the run's artifacts. The build log's "Build" step should print built-in app <key>: included for all seven.
  2. Install it on a machine or VM that has no org_config.json. Open Settings → Connectors. You should see Google (Gmail, Drive and the rest), Slack, Salesforce, Jira, Confluence, Miro and Telegram listed without uploading any bundle.
  3. Sign in to Gmail, Slack, Salesforce, Jira and Miro with your test accounts. Each consent screen should name PrivacyFence. Each row should turn Connected. Then ask your AI client one read per service, for example "list my last 3 emails".

Report back: paste into the PR a line such as ma1: gmail ok, slack ok, salesforce ok, jira ok, miro ok, with "fail: <what you saw>" for any that did not work.

5. Connect an organization server through the relay

ma2-org-relay-signinabout 1–1.5 hours
  1. Deploy the relay from the branch in your own terminal, with the token from mb2 read into CLOUDFLARE_API_TOKEN from your password manager:
    git checkout feature/builtin-oauth-apps
cd cloudflare/oauth-relay && npm ci
CLOUDFLARE_ACCOUNT_ID=326657b4f70af041996d60fd6b8f83fa npx wrangler deploy
printf '%s' "$REVOKE_TOKEN" | npx wrangler secret put REVOKE_TOKEN
    Then curl -sI https://oauth.privacyfence.eu/health should answer 200. Once the PR merges, the deploy workflow takes over.
  2. On a test org server with a public HTTPS hostname, install the branch's wheel. Put a JSON file with the seven apps' IDs and secrets on that server only, mode 0600, owned by the service account, and point PRIVACYFENCE_BUILTIN_APPS at it in the service's environment file. The format is in configuration-reference.md. Use a signed bundle with mode, server and idp only, and no connector sections.
  3. Restart the server. Within a minute, https://oauth.privacyfence.eu/registrations should list your server's host. As an IdP admin, the Admin page's Services section should say "Relay registration: registered".
  4. As a normal user, open /connect and connect Gmail, Slack, Salesforce, Jira and Miro. The browser should pass briefly through oauth.privacyfence.eu and land back on /connect showing Connected.
  5. Check revocation. Run curl -X POST -H "Authorization: Bearer $REVOKE_TOKEN" -H "Content-Type: application/json" -d '{"host":"<your host>"}' https://oauth.privacyfence.eu/admin/revoke. Starting a new Slack connect should now stop on the relay's "not registered" page. Removing a revoked host is not supported, so use a throwaway hostname for this step, or do it last.

Report back: paste into the PR a line such as ma2: registered ok, gmail ok, slack ok, salesforce ok, jira ok, miro ok, revoke ok.

6. Upgrade an org server, then use the Admin page

ma3-upgrade-and-admin-pageabout 45 minutes
  1. On a second test org server running the current release, use an old-style bundle that carries authz, web_push and connector sections for Slack and Google only. Then upgrade it to the branch's wheel and restart. The log should say Imported … settings from org_config.json into org/admin_config.json. The Admin page should show Slack and Google offered and everything else off, with your sign-in restrictions filled in.
  2. Restart again. The log should now warn that org_config.json carries settings that are now managed on the Admin page and are ignored, naming authz and web_push.
  3. As an IdP admin, open Admin. Offer Miro: it asks for your passkey, and Miro appears on /connect without a restart. Withdraw Slack: no passkey, and Slack disappears from /connect.
  4. Change the inline download limit under File delivery. The page should say "Restart PrivacyFence for these changes to take effect: File delivery". Try to turn step-up's require passkey off: the page should not offer it.
  5. Compare Settings as the admin and as a normal user. Both should show the same sections, with no Privacy or Stats. As the normal user there is no Admin item in the header, and opening /admin says "Only administrators can open this page."
  6. On the desktop install from item 4, open Admin, withdraw Miro and check it disappears from Settings → Connectors. Then upload a rooms.json from scripts/sync_room_directory.py --output rooms.json, or skip this step if you have no Workspace room directory.

Report back: paste ma3: import ok, ignored-warning ok, live offer/withdraw ok, restart notice ok, settings same ok, desktop ok into the PR.

7. Try the Docker image on localhost, and check desktop deprecation

ma4-docker-trial-and-deprecationabout 40 minutes
  1. Get the branch's image. Open the build.yml run from item 4 (or dispatch one on feature/builtin-oauth-apps), download the org image artifact for your CPU, and run gunzip -c <file> | docker load.
  2. Run it with no bundle: docker run --rm -p 127.0.0.1:8765:8765 -v pf-trial:/var/lib/privacyfence-org/.privacyfence <loaded image>. The log should show the trial warning and a Trial setup code: XXXX-XXXX line.
  3. Open http://localhost:8765/login. A wrong code should say "That code is not right." Enter the right one, and you land on the passkey page. Enroll a passkey, sign out, then sign back in with the passkey.
  4. Open Admin. The relay line should say "Relay registration: not needed on localhost." On /connect, connect Slack and Gmail. The browser passes through oauth.privacyfence.eu and comes back to localhost:8765.
  5. Add http://localhost:8765/mcp to Claude Code or Claude Desktop. Signing in should send you to the trial login and then the consent page. Then ask for "my last 3 emails" and approve it.

On the desktop install from item 4, check four things: the daemon log has the "Desktop mode is deprecated" line; every Settings, Approvals and Admin page shows the deprecation strip; the companion showed the notice once and not after a restart; and privacyfence_status in your AI client returns a deprecation field.
