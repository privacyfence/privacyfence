What to expect in PrivacyFence 7

Version 7 makes PrivacyFence work out of the box. It ships its own sign-in apps for Google, Slack, Salesforce, Atlassian and Miro, so nobody has to register one before the first connection. It moves day-to-day administration out of the signed file and onto an Admin page. The Docker image can be tried on your own computer in one command. Desktop mode keeps working but is deprecated, and 8.0 removes it.

Before and after

6.x today

  • A fresh install offers no connector until an administrator registers an OAuth app with each provider.
  • One signed org_config.json holds everything: server, IdP, app credentials, which connectors are offered, file delivery, sign-in rules, step-up, audit forwarding and rooms.
  • Any change means rebuilding, re-signing and reinstalling that file with build_org_bundle.py.
  • Org admins edit privacy and see Stats inside Settings.
  • The Docker image refuses to start without a bundle and an IdP.

7.x

  • Built-in PrivacyFence apps cover any provider you haven't set up yourself, on servers and in single-user Docker (not in desktop mode).
  • org_config.json shrinks to startup settings and credentials. It is still signed.
  • Everything operational lives in admin_config.json and is changed on the Admin page, with a passkey for sensitive changes.
  • Settings is personal and looks the same for everyone, admin or not.
  • With no bundle, docker run starts in single-user mode on http://localhost:8765.

Three places configuration lives

org/org_bundle.jsonBuilt offline, signed, installed by you. 7.x copies it once from 6.x's org_config.json.
  • mode, server, idp (all three can also come from environment variables)
  • Your own app credentials, only for providers where you don't want the built-in app
  • A Grist OAuth app, if you use one
org/admin_config.jsonWritten by PrivacyFence, edited on the Admin page
  • Which services are offered
  • Grist and Peek server addresses (unless the server's environment sets them), Jira Assets, rooms, unattended sessions
  • Org mode: automatic Peek and Grist accounts, on or off
  • Org mode: file delivery, web push, sign-in restrictions, step-up (stricter only), scoped tokens, audit forwarding
Built into the releaseBaked in at build time, like Telegram's
  • PrivacyFence's own Google, Slack, Salesforce, Atlassian and Miro apps, in the org image and the PyPI wheel
  • Used on servers and in single-user mode for any provider the bundle leaves out; desktop mode never uses them
  • Public in effect; every sign-in still asks the person for consent

Which app a service uses: your credentials in the bundle if they are there, otherwise the built-in app. Whether it is offered at all: the Admin page. Automatic Peek and Grist accounts are switched on there too, but their key only goes to addresses set in the server's environment (PRIVACYFENCE_PEEK_BASE_URL, PRIVACYFENCE_GRIST_SERVER_URL, PRIVACYFENCE_GRIST_PROVISIONER_URL), so the page cannot redirect it.

The Admin page

  • It is a new top-level menu item next to Settings. On a server it is visible only to IdP administrators. On a desktop install, the install owner sees it.
  • Services: switch each service on or off, and see whether it uses your own app or the built-in one, and on a server whether the relay is registered.
  • Features: Grist and Peek addresses, Jira Assets, the room directory (upload the file sync_room_directory.py --output writes), and unattended sessions.
  • Server only: File delivery, Access (sign-in restrictions), Step-up, Scoped tokens, Audit forwarding, Privacy and Stats.
  • Service switches take effect at once. Most server settings take effect at the next restart, and the page tells you which ones are waiting.
  • Every sensitive change on the Admin page needs your passkey, whatever the step-up setting. An admin without a passkey is sent to add one first.
  • Step-up can only be made stricter here. Relaxing it stays a deliberate file edit plus a restart.
  • The audit-forwarding token's environment-variable name is shown but not editable. Otherwise an admin could send any server secret to a URL of their choosing.
  • Uploading a room directory needs a passkey, because room names reach the AI client.

Starting a new organization server

  1. DNS. Point a name such as pf.acme.example.com at a host with Docker.
  2. One app at your identity provider. Register an OIDC app in Google Workspace, Entra ID or Okta with three redirect URIs: /oauth/idp/callback, /oauth/idp/login-callback and /oauth/stepup/callback on your name. This is the only app you register. Connectors use the built-in apps.
  3. An env file. Copy privacyfence.env.example to privacyfence.env and fill it in:
    PRIVACYFENCE_ISSUER_URL=https://pf.acme.example.com
PRIVACYFENCE_IDP_ISSUER=https://accounts.google.com
PRIVACYFENCE_IDP_CLIENT_ID=…
PRIVACYFENCE_IDP_CLIENT_SECRET_FILE=/run/secrets/idp_client_secret
PRIVACYFENCE_ADMIN_EMAILS=alice@acme.example.com
PRIVACYFENCE_TRUSTED_PROXIES=172.30.87.2
    Put the client secret in a Docker secret file, so it doesn't show in docker inspect. Set PF_HOSTNAME in .env for Caddy.
  4. Optional: Peek and Grist. Add their addresses, and the provisioning keys if you want automatic accounts:
    PRIVACYFENCE_PEEK_BASE_URL=https://peek.acme.example.com
PRIVACYFENCE_PEEK_PROVISIONING_KEY_FILE=/run/secrets/peek_provisioning_key
PRIVACYFENCE_GRIST_SERVER_URL=https://grist.acme.example.com
PRIVACYFENCE_GRIST_PROVISIONER_URL=https://grist-provisioner.acme.example.com
PRIVACYFENCE_GRIST_PROVISIONING_KEY_FILE=/run/secrets/grist_provisioning_key
    The keys come from Peek and the Grist provisioner. Keep them in Docker secrets too. You switch automatic accounts on later, on the Admin page. Without these variables you can still type a Peek or Grist address on the Admin page, but automatic accounts then stay unavailable.
  5. Start. Run docker compose up -d. Caddy gets the TLS certificate, and the image starts in organization mode. There is no bundle to build or sign.
  6. Turn services on. Sign in as the admin email, open Admin → Services, and offer the services you want. For Peek and Grist, turn on Automatic accounts if you set their keys (it asks for your passkey and takes effect after a restart). With Entra ID, also tick "Trust email addresses the identity provider does not mark verified", because Entra never marks an address verified. The server registers itself with the relay, and people can connect at /connect.

You still need a signed org_bundle.json if you want your own connector apps, or a configuration nobody can change without your signing key. A bundle wins over the environment. Admins by email need an IdP that sends email_verified; with Entra ID, use the group claim instead. With Google as the IdP, use an Internal consent screen or set allowed domains on Admin → Sign-in, because any Google account can verify an address. One Google OAuth client can also sign people in to Peek and Grist, but a separate client per service is easier to rotate or revoke.

Upgrading an existing server from 6.x

  1. Install 7 and restart. You don't need to change anything first.
  2. 7 copies org_config.json and its signing-key and serial pins to new names (org_bundle.json, org_bundle_signing_pubkey.txt, org_bundle_serial.txt). It never changes or deletes 6.x's files.
  3. On this first start, PrivacyFence copies the operational settings out of your current org_config.json into admin_config.json, and logs that it did. The connectors your bundle offered stay exactly the ones offered. A provider you add to the bundle later also needs switching on, on the Admin page.
  4. From then on those sections in the bundle are ignored, and each start logs a warning naming them. Rebuild the bundle with only the startup and credential flags; build_org_bundle.py now refuses the moved flags and names each one.
  5. Automatic Peek and Grist accounts (6.11). They keep working. The Peek, Grist and provisioner addresses from your bundle are kept, locked, and the on/off switch moves to the Admin page. To change an address later, set PRIVACYFENCE_PEEK_BASE_URL or the Grist variables on the server. Rebuilding the bundle with --peek-auto-provision or --grist-auto-provision is refused from 7.0.
  6. Changed your mind? Stop 7 and install the latest 6.x (6.11.x if you use automatic accounts, otherwise 6.10.0 or newer). It runs with the org_config.json it always had. Admin page changes and bundles installed under 7 don't carry back. To upgrade again from 6.x's current files, first delete org_bundle.json, org_bundle_adopted.json, the two new pin files and admin_config.json.
  7. Back up admin_config.json with the rest of the data volume. It is not signed, so it gets the same file protection as the install-wide settings.

Single-user mode: the Docker image on your computer

docker run --rm -p 127.0.0.1:8765:8765 \
  -v pf-data:/var/lib/privacyfence-org/.privacyfence \
  ghcr.io/privacyfence/privacyfence-org:latest
  1. With no bundle, the image starts in organization mode in single-user mode, with one administrator and no identity provider. It only runs at http://localhost or 127.0.0.1.
  2. docker logs shows a one-time setup code. Open http://localhost:8765/login, enter it, and enroll a passkey. From then on, you sign in with the passkey.
  3. Connect services on /connect. The built-in apps send the provider's redirect through oauth.privacyfence.eu, which bounces your browser straight back to localhost. Nothing is registered and nothing is stored there.
  4. Add http://localhost:8765/mcp to Claude Code or Claude Desktop. It signs in through the same single-user sign-in and consent page.
  5. To move to a multi-user server, add the PRIVACYFENCE_IDP_* variables and a public https PRIVACYFENCE_ISSUER_URL to privacyfence.env (or an idp section in a signed org_bundle.json). Your admin settings and connections carry over.

Keep the 127.0.0.1: in the port mapping. Inside the container PrivacyFence has to listen on every interface, and only that mapping keeps it off your network.

Single-user mode does not protect you from an AI agent on the same computer. Anything that can run docker, read docker logs or open a page on another localhost port can take over the install. Step-up (a passkey for writes and personal-data reads) is on by default to limit that, but for real separation run it under a separate OS account (rootless Docker) or in a VM, or use an organization server.

Organization servers and the relay

  • A server that uses a built-in app sends people's sign-in redirects through https://oauth.privacyfence.eu. That is a small Cloudflare Worker that forwards the browser to your server and keeps no logs.
  • On a new server, built-in services start off. Offering the first one on the Admin page is your opt-in to the relay. Single-user mode starts with them on. A desktop install has no built-in apps at all.
  • Your server then registers itself automatically by serving a token at /.well-known/privacyfence-relay. That proves it controls its domain. It re-registers daily, and registrations expire after 35 days without one.
  • Needs: an https:// address with no path, reachable from the internet at that one path, and outbound HTTPS to oauth.privacyfence.eu. A server behind an IP allow-list or a VPN keeps using its own apps.
  • Every new registration emails the maintainers at info@privacyfence.eu with the host, time, IP address and a ready-made revoke command. There is no waiting period. Suspicious hosts are revoked from the email.
  • Registered host names are visible only to PrivacyFence maintainers (/registrations needs the maintainer token), and maintainers can revoke any host. A server's well-known token is served only once it actually needs the relay, so nobody else can register it first.
  • Slack and Miro sign-ins don't use PKCE, so their sign-in codes pass through the relay usable. The Admin page says so on those rows. Use your own Slack or Miro app to avoid it.

How the relay is released

  • Its own track. The relay is a service PrivacyFence runs, like downloads.privacyfence.eu. Operators never install it, and app releases never deploy it.
  • How it deploys. The deploy-oauth-relay-worker GitHub workflow deploys it whenever a change under cloudflare/oauth-relay/ reaches main, or when you run the workflow on main. A test job runs first, and a /health smoke test runs after.
  • First deploy. You do it by hand from the feature branch (step 4 below), so the end-to-end checks can run before the pull request merges. The merge then redeploys the same code through the workflow.
  • Before tagging 7.0.0. /cut-release and docs/releasing.md check that https://oauth.privacyfence.eu/health answers 200.
  • Compatibility. The relay's routes only grow. Every relay version keeps serving every released 7.x server, and a breaking change gets a new path while the old one stays.
  • Runbook. docs/oauth-relay.md covers setup, smoke tests, revoking a server, rotating the revoke token and rolling back. It is a contributor doc, not published on the website.

The website and the relay terms

  • On merge, together with the relay: a new /relay-terms/ page (free, as is, no warranty, liability limited as far as the law allows, can change or stop at any time, operators are responsible for their own servers, abuse gets a host revoked), linked from the footer and from the relay itself (oauth.privacyfence.eu/ redirects there).
  • The privacy policy gains a Sign-in relay section: what the relay processes, the host list only maintainers see, no Worker logs, and the registration emails (host, IP, country).
  • Every "there is no PrivacyFence-operated server" sentence (home, enterprise, how it works, security, FAQ, compare) is corrected: no data passes through PrivacyFence; only sign-in redirects for the built-in apps pass through the relay.
  • The download page and the FAQ say that PrivacyFence 7 deprecates desktop mode and 8 removes it.
  • After you tag 7.0.0: a follow-up website PR (step 13) rewrites the product and connector pages for 7.x, because they link docs that exist only once the stable release is out.
  • The terms were written from the plan, not by a lawyer. Step 13 asks you to have them reviewed.

The new live-check runner: runner.privacyfence.eu

  • A fresh host. A Hetzner Cloud server that does nothing but PrivacyFence's live checks. The weekly connector-live-check and qa-record-fixture move to it, under a new label and runner group, privacyfence-live. The old runner keeps serving main until the merge switches the label. Then you remove it.
  • It tests the built-in apps. The QA tokens are re-minted with PrivacyFence's own apps, and the runner's bundle becomes optional. The workflows write the built-in credentials into the checkout from repository secrets, and delete them again at the end of each run.
  • Behind Cloudflare, administered over Tailscale. runner.privacyfence.eu is a proxied DNS record. The server's firewall accepts only HTTPS from Cloudflare. SSH is closed: you reach the box with Tailscale SSH.
  • Separation. The GitHub runner runs as pfrunner, which has no sudo and is not in the docker group. Peek and the QA org server are containers that cannot see its files.
  • A QA organization server. https://runner.privacyfence.eu serves a PrivacyFence org server signed in with the QA Google Workspace. It is the public host the relay test needs, and it stays for later manual QA.
  • A weekly relay check. The live check also tests oauth.privacyfence.eu/health and reports relay: up or down.

Provider caveats with the built-in apps

  • Google: verification can only start after the merge, because it needs a video of the real flow and the live privacy policy (step 11). Until Google approves, people see an "unverified app" screen, and the app is capped at 100 users in total. So 7.0 may ship unverified; its release notes point organizations to their own Google app, which has no cap if it is Internal. Do not tell Workspace admins to mark the built-in app as trusted (SEC-02).
  • Salesforce: orgs that block uninstalled connected apps need their admin to install or approve PrivacyFence once.
  • Slack: workspaces that require app approval need their admin's approval once. Until PrivacyFence is listed in the Slack Marketplace (step 12), Slack limits channel and thread reads for the built-in app to 1 request per minute and 15 messages per call; a workspace's own internal Slack app avoids that, and the Admin page says so.
  • Switching a service between the built-in app and your own makes everyone who connected Salesforce, Atlassian or Miro connect again.

7.x is the stepping stone to 8

  • Every 7.x start upgrades all stored data for every person: old rule formats, old verb names, and tokens that still name rules. Today some of this only happens when a person signs in.
  • When nothing old is left, it writes data_format.json ("format": 7) next to the data. It goes into your backups and the Docker volume like everything else.
  • The Admin page says Ready for PrivacyFence 8: yes, or lists what still blocks it, for example a person's settings that cannot be converted.
  • 8.x drops all the old upgrade code. It refuses data without the marker: "Install PrivacyFence 7.x, start it once, then install this release." Its installers can check the same file before replacing anything.
  • 7.x also refuses data that 8.x has already written, so a downgrade can't half-read it.

Desktop mode: 7 deprecates, 8 removes

6.xDesktop mode and organization servers, side by side.
7.xDesktop mode still works, with a notice in the log, in privacyfence_status, on every page and once from the menu-bar or tray app. It gets no built-in apps: providers still need your own app in the bundle. A new guide covers moving to a server or Docker single-user mode.
8.0Desktop mode is removed: the companion, installers and Claude Desktop shim. That is a separate plan, written after 7.0 ships.

You cut 7.0.0 with /cut-release once the pull request merges. The changelog marks it as breaking.
