Peek auto-provisioning: checks after implementation

These checks cover what CI cannot: a real Peek server, your identity provider and two servers in separate network zones. Do them after the feature PR feature/peek-auto-provisioning is ready, and before you merge it. The Peek side (feat/pf-provisioning in andras-tkcs/peek) must already be merged and released.

Secrets. The Peek provisioning key never goes into chat, the PR, a ticket or the bundle. It goes straight from Peek's output into your password manager and the PrivacyFence server's environment file.

Before implementation

Nothing. The phases build and test against fakes.

After implementation

1. Peek release and provisioning key

about 20 min

This proves the wire contract against a real Peek server.

  1. Open Peek's releases and pick the first release that lists provisioning keys.You should see a release published after the feat/pf-provisioning PR merged.
  2. Upgrade your Peek server to that release, as in Peek's Upgrades and rollbacks. For Docker, pin the tag: ghcr.io/andras-tkcs/peek:<version>.Peek starts and /readyz answers 200.
  3. From the PrivacyFence server's network zone, check that the API exists:
    curl -s -o /dev/null -w '%{http_code}\n' https://peek.example.com/api/provisioning/self
    Expect 401, which means the API is there and wants a key. 404 means the release is too old. A timeout means the firewall blocks PrivacyFence → Peek.
  4. On a machine where peek is signed in as a Peek admin, run:
    peek provisioner create --name PrivacyFence
    It prints a key that starts with peekprov_, once.
  5. Copy the key into your password manager now. Do not paste it anywhere else.
  6. Open Peek's Admin page.The Provisioners card lists PrivacyFence with last used "never" and 0 accounts.
Done when

The Provisioners card lists PrivacyFence and /api/provisioning/self answers 401 from the PrivacyFence zone.

2. Key in PrivacyFence, bundle rebuilt

about 15 min

This exercises the key read from the environment, bundle validation and the startup check on a real install.

  1. systemd: add the key to /etc/privacyfence-org.env (owned by root, mode 0600) as one line, PRIVACYFENCE_PEEK_PROVISIONING_KEY= followed by the key, with sudoedit /etc/privacyfence-org.env. In /etc/systemd/system/privacyfence-org.service, uncomment EnvironmentFile=/etc/privacyfence-org.env, then run sudo systemctl daemon-reload. See Hardened systemd unit.Docker: put the same line in privacyfence.env next to compose.yaml instead (org-mode Docker).
  2. Rebuild the bundle with your usual flags plus --peek-auto-provision. Keep --peek-base-url. Follow Changing a bundle later and Install the bundle.The builder accepts it. Without --mode org or a Peek address, it refuses with a message naming the missing flag.
  3. Restart PrivacyFence (sudo systemctl restart privacyfence-org, or docker compose up -d), then read the log:
    journalctl -u privacyfence-org --since "5 min ago" | grep -i "peek provisioning"
    Expect Peek provisioning ready at peek.example.com (0 accounts managed). "is not set" means the environment file did not load. "HTTP 401" means the key is wrong.
Done when

The "ready" line is in the log.

3. Three people: new, existing, admin

about 20 min

This verifies create, adopt and the admin refusal against the real Peek server and identity provider.

  1. Prepare three test identities in your identity provider: A has no Peek account, B already has a non-admin Peek account with a page, and C is a Peek admin. All three may sign in to PrivacyFence.
  2. In a private window, sign in to PrivacyFence as A at https://pf.example.com/connect. Wait a few seconds and reload.Peek shows Connected with "Your organization connected your Peek account automatically."
  3. On Peek's Admin page, find A under Users.A shows the badge Managed by PrivacyFence.
  4. In an AI client connected as A, ask it to list your Peek pages.peek_list_pages runs without a sign-in prompt and returns an empty list.
  5. Repeat steps 2 and 4 as B.B is Connected, and peek_list_pages lists B's existing page. Nothing was lost.
  6. Sign in as C.Peek stays Not connected, and Connect Peek works by hand. The PrivacyFence log has Peek provisioning for <C's id>: admin.
Report back

4. Each works without the other

about 15 min

This proves neither product needs the other, which CI cannot show across two servers.

  1. Stop Peek (docker stop peek or its service). Sign in to PrivacyFence as a fourth test person D.Sign-in finishes at normal speed and the other connectors work. The log has a Peek provisioning for <D's id> warning that says Peek could not be reached.
  2. Start Peek again. Within six hours, or at D's next sign-in, D becomes Connected.To check right away, sign out and back in as D.
  3. Stop PrivacyFence. Sign in to Peek's own web page as A through Peek's OAuth sign-in, and as a Peek user who is not a PrivacyFence user.Both reach the dashboard, open pages and comment. Peek's log shows no attempt to reach PrivacyFence.
  4. Start PrivacyFence again.

5. Release a person

about 10 min

This verifies the offboarding call against the real Peek server.

  1. Find A's principal id on the PrivacyFence Settings page or in the audit log.
  2. systemd: run it as the daemon's account, with the environment file loaded and without putting the key on the command line:
    sudo systemd-run --pipe --wait -p User=privacyfence-org \
  -p EnvironmentFile=/etc/privacyfence-org.env \
  /opt/privacyfence/venv/bin/privacyfence-app --peek-release <A's id>
    Docker: docker compose exec privacyfence privacyfence-app --peek-release <A's id>. Expect: "Released the Peek connection of …; PrivacyFence's Peek token for it is revoked. The Peek account stays."
  3. In Peek, sign in as A and open the dashboard's API keys.The PrivacyFence key is gone, and A's pages are still there.
  4. Remember: if A signs in to PrivacyFence again, A is provisioned again. Release is for people who can no longer sign in, so remove them from the identity provider first.
Report back

Paste into the PR: ma5: release PASS/FAIL.
