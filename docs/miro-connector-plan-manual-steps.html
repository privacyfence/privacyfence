PrivacyFence · plan/miro-connector

Miro connector: the steps only you can do

Do the three Before implementation tasks before you run /implement. The QA-recording phase needs them. Task 2 also confirms how Miro wants its token request, and task 3 tries the writes no CI run can try before the merge. Do checks 4 and 5 once the feature PR is up, and tick them in the PR. Do check 6 after it merges. Your ticks here are saved in this browser only.

Part 1

Before implementation

1. Create a Miro QA account, Developer team, QA app and two boards

mb1-miro-qa-appabout 25 min

Phase p11 records live fixtures from the seed board through this app. Task 3, and after the merge the weekly live check, add and change test sticky notes on the lifecycle board. Use an account that holds nothing real. A free Miro plan is enough: it allows three editable boards, and this needs two.

The client secret lets anyone holding it exchange sign-in codes for your QA account. Never paste it into a chat, the plan, a PR, an issue or a GitHub secret. Its only other copy is the runner's bundle in task 2 (ADR 0019).

Done when: the QA app exists with expiring tokens, only boards:read and boards:write, and the redirect URI http://localhost:53686/callback; its client ID and secret are in your password manager; and both boards exist as described, with their ids noted.

2. Put the app, a Miro token and the board ids on the QA runner

mb2-runner-qa-stateabout 20 min

Phase p11 dispatches qa-record-fixture.yml (on main, for the phase branch), which copies ~/privacyfence/ from the runner into its checkout (connector-qa.md, Persistent QA state). PrivacyFence's own --miro-oauth doesn't exist until the feature is built, so you get the first token by hand here. The runner then refreshes it on every run and copies the new one back. This request is also the plan's test of whether Miro accepts the token request as a form body.

The token file and the bundle hold live credentials for the QA account. They stay on the runner, mode 600, and nowhere else. The token's refresh window is 60 days. If more than 60 days pass before phase p11 runs, repeat steps 5 to 9.

Done when: on the runner, org/org_config.json has a miro section and still loads (re-signed if it is signed); credentials/miro_token.json has mode 600 and holds access_token, refresh_token, "expires_at": 0 and team_id; and qa_environment.yaml has a miro section with board_id and lifecycle_board_id. Confirm only if step 7 printed ok: form body accepted. Go straight on to task 3: its token lasts one hour.

3. Run the Miro write probe on the lifecycle board

mb3-miro-write-probeabout 5 min · within the hour after task 2

No CI run can try Miro writes against a feature branch: the runner only runs workflows as they are on main, and the weekly live check tests main's code. So the three write behaviours the plan relies on are tried here by hand before anything is built on them. They are creating a frame, a shape fill color from Miro's documented list, and taking an item out of a frame with {"parent": null}, which Miro doesn't document. The probe uses the access token task 2 just saved, which lasts one hour. It never refreshes it, so the token file stays valid.

Done when: the probe printed frame created, bulk created 2 items, fill color accepted and move-out works. If any line says something else, or the probe stopped with "refused", do not confirm this task. Paste its output to the planning session instead: the plan has to be revised before /implement starts. For a failed move-out, that revision is the fallback the plan already describes in §6. Then tell the /implement session that all three before-steps are done.

Part 2

After implementation

4. Sign in to Miro from Settings and drive every Miro tool

ma1-local-mode-checkabout 40 min

This is the first real browser sign-in (the recorded checks use the hand-made token). It also shows what each approval card contains, and that real writes land on the board.

Report back: tick the item in the PR and paste one line, for example ma1 local mode: PASS (sign-in, 3 auto, 4 review cards, batch of 5, connector, updates incl. frame move, board rename, link refused, rule, revoke), or FAIL at step N: what you saw.

5. Connect Miro on /connect in an org-mode test deployment

ma2-org-mode-checkabout 20 min · only if you run one

Checks the bundle's miro section, the org redirect URI and the server-side code exchange. No CI job runs an org deployment against Miro.

Report back: tick the item in the PR and paste ma2 org mode: PASS, FAIL at step N: what you saw, or ma2: skipped, no org-mode test deployment.

6. Check the Miro lifecycle row on main after the merge

ma3-lifecycle-on-mainabout 10 min · after the feature PR merges

The lifecycle (add, change, move out of a frame on the lifecycle board) runs only in connector-live-check.yml, which checks main's code. This is the first time it runs through PrivacyFence's own Miro client.

Report back: ma3 lifecycle on main: PASS (run URL), or FAIL: the row's note. A failure here is a bug to fix on main in a new PR.
