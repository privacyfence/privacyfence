Part 1

Before implementation

1. Add the account comment endpoint to your Peek fork

mb1-fork-comment-endpointone Peek session, plus deploy

Peek's comment API takes no token today: it posts as whatever name the browser sends, and on a public page as "anonymous". PrivacyFence posts only through a separate route that takes the token and signs the comment with your account name. The browser route stays as it is. The contract is plan §3.1; the prompt below carries all of it.

/devflow:make-plan prompt
Add a token-authenticated comment endpoint, so an API client can post a comment under its own account name.

Why: PrivacyFence (an approval gateway between AI assistants and services) is adding a Peek connector. Its agent reads comments with GET /api/uploads/{slug}/comments and a bearer token, but cannot post one: POST /api/uploads/{slug}/comments has no token path. It ignores the Authorization header, checks only the browser's page access (viewerCanAccessUpload), and takes the author name from the request body, so on a public page an API call would post as "anonymous". PrivacyFence must never post an unsigned comment the user approved.

What to build:
- A new route, registered with the other token-gated API routes in internal/server/routes.go:
  POST /api/uploads/{slug}/account-comments, wrapped in s.authToken(...).
- A new route on purpose, not a token branch inside the existing handler: on a server without it, the client's call fails (404/405) instead of silently posting as "anonymous". The browser route POST /api/uploads/{slug}/comments and its behaviour stay exactly as they are.
- Who may post: the token's account must own the upload or be an admin, the same rule as the token path of handleListComments. Otherwise 403 {"error":"not owner"}. Unknown slug: 404 {"error":"not found"}. Missing, invalid or disabled token: whatever authToken already answers (401/403).
- Request body JSON: {"body", "selector", "element_text", "anchor_kind"}. Any "name" field is ignored. Same trimming, normalizeCommentAnchorKind handling, required body and length limits (body 4000, selector 500, element_text 200) and error answers as handleAddComment; share that validation rather than copying it.
- The author is the token's account name. The per-comment visitor hash is derived from the account id (with the server secret), not from a visitor cookie; no cookies are set.
- The same comment rate limiter as the browser route.
- An audit entry "comment.create" with the slug, like the other token routes' auditRequest calls.
- Answer 200 with the new comment only, as a single commentOut object: {"id","selector","element_text","anchor_kind","author","body","created_at"} (created_at Unix seconds). Not the whole list.

Tests (internal/server, next to comments_test.go): no token → 401; a token for another account's upload → 403; an admin token on someone else's upload → 200; success → 200, author is the account name even when the body carries "name"; empty body → 400; an over-long field → 413; an invalid anchor kind → 400; the comment then appears in GET .../comments; the browser route still behaves as before (an existing test covering it keeps passing).

Docs: add the route to the API reference page (reference.md in the Astro docs site's content folder, src/content/docs under the docs directory) and wherever else the token API routes are listed, and a line in the skills/peek SKILL.md only if it documents API routes.

Out of scope: no CLI command, no change to the browser comment route, the page UI, the GET comments endpoint or anything else. View restrictions are a separate change.

This is one small change: hand back a single-session prompt, not a plan.

Done when: a POST to /api/uploads/<a page you own>/account-comments with your token and {"body":"[QATEST] probe"} answers 200 with your account name as author, and the same request without the Authorization header answers 401.

3. Put the QA token and the seed slug on the QA runner

mb3-runner-qa-stateabout 10 min

Phase p9 dispatches qa-record-fixture.yml, which copies ~/privacyfence/ from the runner into its checkout (connector-qa.md, Persistent QA state). PrivacyFence's own --peek-login does not exist until this plan lands, so the token comes from Peek's CLI.

The token acts as the QA account. Never paste it into a chat, the plan, a PR, an issue or a GitHub secret. Its only working copy is the runner file (ADR 0019).

Done when: on the runner, ~/privacyfence/credentials/peek_token.json exists with mode 600 and holds base_url and token; qa_environment.yaml has peek: with page_slug:; and the runner's org_config.json has no peek section, or one whose base_url matches. Then tell the /implement session that the three before-steps are done.
