Peek connector: the steps only you can do

Do the three Before implementation tasks before you run /implement; the QA-recording phase needs all of them. Do the After implementation checks once the feature PR is up, and tick them in the PR. Your ticks here are saved in this browser only.

Part 1

Before implementation

1. Add the account comment endpoint to your Peek fork

mb1-fork-comment-endpointabout 45 min

Peek's comment API takes no token today: it posts as whatever name the browser sends, and on a public page as "anonymous". PrivacyFence posts only through a separate route that takes the token and signs the comment with your account name. The browser route stays as it is. The exact contract is in plan §3.1.

Done when: a POST to /api/uploads/<a page you own>/account-comments with your token and {"body":"[QATEST] probe"} answers 200 with your account name as author, and the same request without the Authorization header answers 401.

2. A QA Peek server, a QA account and a seed page

mb2-peek-qa-serverabout 20 min

Phase p9 records live fixtures from this page, and the weekly live check publishes, comments on and deletes a scratch page with this account. Use a server and an account that hold nothing real.

Done when: the QA server is reachable over https from the runner, the QA account owns the private page PrivacyFence QA [QATEST].html with one comment containing [QATEST], and you have its slug.

3. Put the QA token and the seed slug on the QA runner

mb3-runner-qa-stateabout 10 min

Phase p9 dispatches qa-record-fixture.yml, which copies ~/privacyfence/ from the runner into its checkout (connector-qa.md, Persistent QA state). PrivacyFence's own --peek-login does not exist until this plan lands, so the token comes from Peek's CLI.

The token acts as the QA account. Never paste it into a chat, the plan, a PR, an issue or a GitHub secret. Its only working copy is the runner file (ADR 0019).

Done when: on the runner, ~/privacyfence/credentials/peek_token.json exists with mode 600 and holds base_url and token; qa_environment.yaml has peek: with page_slug:; and the runner's org_config.json has no peek section, or one whose base_url matches. Then tell the /implement session that the three before-steps are done.

Part 2

After implementation

4. Connect Peek in Settings and drive every Peek tool

ma1-local-mode-checkabout 30 min

Proves the sign-in dialog against a real Peek, what the approval cards show, and that real writes land. Unit tests and the recorder cannot show any of that.

Report back: tick the item in the PR and paste one line, for example ma1 local mode: PASS (sign-in errors, 2 review cards without IPs, publish/visibility/comment/delete cards, password hidden), or FAIL at step N: what you saw.

5. Connect Peek on /connect in an org-mode test deployment

ma2-org-mode-checkabout 20 min · only if you run one

Proves the bundle's peek section and the per-person device sign-in on /connect. No CI job runs an org deployment against Peek.

Report back: tick the item in the PR and paste ma2 org mode: PASS, FAIL at step N: what you saw, or ma2: skipped, no org-mode test deployment.
