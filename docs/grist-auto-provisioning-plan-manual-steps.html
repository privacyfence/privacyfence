PrivacyFence · plan/grist-auto-provisioning

Grist auto-provisioning: the steps only you can do

Two plans share this page. The Grist provisioner is a new service in its own repository; it needs one step before its build starts. PrivacyFence's phases test against fakes, but its last phase deletes the provisioner's plan from the PrivacyFence repository, so item 1 (which copies that plan into the new repository) comes first for both. Once both are built, the five checks under After implementation prove the whole chain on your real Grist and Google set-up.

Never paste a key into a chat, the plan or this page. Each step says where a key goes.

Before implementation

Before the provisioner's build starts

Both /implement runs wait for this item: PrivacyFence's as mb1-companion-plan, the provisioner's as mb1-repo.

1. Create the provisioner repository

mb1-repoabout 15 min
  1. Open New repository in the privacyfence organization. Name it grist-provisioner, pick the visibility you want, tick Add a README file, and choose the Apache License 2.0.You land on the new repository's front page with README.md and LICENSE.
  2. Add a file CHANGELOG.md with exactly these two lines:
    # Changelog

## [Unreleased]
  3. Add .claude/toolkit.yaml with the profile from the companion plan, section Manual steps. Copy it as it is.
  4. Copy the companion plan into the new repository: create a branch plan/grist-provisioner and add the companion plan there as docs/grist-provisioner-plan.md. You can also ask a Claude Code session on the new repository to do this step.
  5. In the Claude Project you use for this repository, enable the devflow plugins (devflow and stack-python), the same way they are enabled for PrivacyFence (ADR 0132).A new Claude Code session on the repository lists /implement.
  6. Make sure GitHub Actions is allowed for the repository (Settings → Actions → General), and that workflows may write packages, so the release workflow can push the Docker image to GHCR.
Done when: .claude/toolkit.yaml is on main and passes devflow's validate_profile.py, and a session on the repository lists /implement. Then run /implement https://github.com/privacyfence/grist-provisioner/blob/plan/grist-provisioner/docs/grist-provisioner-plan.md.
After implementation

Before the PrivacyFence PR merges

These need the provisioner's first release and PrivacyFence built from the feature branch. Report each result in the PrivacyFence PR.

1. Deploy the provisioner next to Grist and create a key

ma1-provisionerabout 30 min
  1. On the Grist host, back up Grist's /persist volume (it holds home.sqlite3, where the provisioner will write keys).
  2. Add the provisioner to Grist's compose file, as in the provisioner's README. It must share Grist's persist volume and run on the same host. Use the same GRIST_ADMIN_EMAIL and GRIST_DEFAULT_EMAIL values as your Grist service (at least one is required), and run it as Grist's grist user so it can write the database: 
      grist-provisioner:
    image: ghcr.io/privacyfence/grist-provisioner:<version>
    user: "<uid>:<gid>"   # from: docker compose exec grist id grist
    volumes:
      - <grist persist volume>:/persist
      - grist-provisioner-data:/data
    environment:
      GRIST_ADMIN_EMAIL: <same as Grist>
      GRIST_DEFAULT_EMAIL: <same as Grist>
      PROVISIONER_ALLOWED_DOMAINS: <your email domain>
    restart: unless-stopped
  3. Run docker compose up -d grist-provisioner, then docker compose exec grist-provisioner grist-provisioner check.You see ok: N Grist users, 0 linked. A schema error means your Grist version is not supported yet; stop and report it.
  4. Publish it through your TLS reverse proxy at an address such as https://grist-provisioner.example.com, and allow only the PrivacyFence server's address to reach it.From the PrivacyFence server, curl https://grist-provisioner.example.com/healthz answers ok; from anywhere else it is refused.
  5. Run docker compose exec grist-provisioner grist-provisioner create-key --name PrivacyFence. It prints a key starting with gristprov_ once.
    Do not store it anywhere but the next step's environment file. If you lose it, revoke it with revoke-key and create a new one.
Report: ma1: pass, provisioner <version> on grist-core <version>, or what failed.

2. Give PrivacyFence the key and turn it on

ma2-pf-configabout 20 min
  1. On the PrivacyFence server, put PRIVACYFENCE_GRIST_PROVISIONING_KEY=<the key> into the daemon's environment file: /etc/privacyfence-org.env (mode 0600, owned by root) with the unit's EnvironmentFile= line enabled, as in the hardened systemd unit; or, with Docker, privacyfence.env as in Organization mode with Docker.
  2. Rebuild the bundle from the feature branch, the same way you built it before (Grist setup → Build and distribute the bundle), adding: 
    python3 scripts/build_org_bundle.py --merge -o org_config.json \
  --grist-auto-provision \
  --grist-provisioner-url https://grist-provisioner.example.com
    The bundle must keep --grist-server-url and must not have a Grist OAuth app; the builder refuses otherwise. Sign and install it as usual.
  3. Restart the PrivacyFence daemon and read its log.You see Grist provisioning ready at grist-provisioner.example.com (0 accounts managed). … is not set means the environment file was not loaded; refused the provisioning key means the key was copied wrongly.
Report: ma2: pass, with the ready line, or what failed.

3. Check four kinds of people

ma3-four-peopleabout 30 min

The state of each person is in <data dir>/users/<principal id>/credentials/grist_provisioning.json on the PrivacyFence server. Provisioning runs within seconds of a sign-in.

  1. No key yet: a person who has signed in to Grist once and never made an API key signs in to PrivacyFence./connect shows Grist connected and "Your organization connected your Grist account automatically." The state says provisioned. In Grist, their Profile → API now shows a key. Ask the assistant to list their Grist documents.
  2. Own key: a person who already made a key in Grist signs in to PrivacyFence.Connected, state adopted, and the key in Grist is the same as before (their own scripts still work).
  3. Install admin: the GRIST_ADMIN_EMAIL (or GRIST_DEFAULT_EMAIL) person signs in to PrivacyFence.Not connected; state admin. They can still paste a key on /connect.
  4. No Grist account: someone who has never used Grist signs in to PrivacyFence, then signs in to Grist once, then signs in to PrivacyFence again.First state no_account, then provisioned after the second sign-in (or within six hours without one).
Report: ma3: provisioned / adopted / admin / no_account→provisioned, marking any that differ.

4. Check that sign-in never waits on Grist

ma4-independenceabout 15 min
  1. Run docker compose stop grist-provisioner on the Grist host, and sign in to PrivacyFence as a new test person.Sign-in finishes as fast as usual. The state says error with Could not reach the Grist provisioner….
  2. Start it again (docker compose start grist-provisioner) and sign in once more.The state becomes provisioned.
  3. Stop Grist itself for a minute and sign in to PrivacyFence.Sign-in still works; only the Grist tools fail until Grist is back.
Report: ma4: pass, or which step blocked sign-in.

5. Check release

ma5-releaseabout 10 min
  1. Remove the "No key yet" test person from Google Workspace (or your PrivacyFence authorization rules) first, so they cannot sign in again.
  2. As the account the daemon runs as, with the key in the environment, run privacyfence-app --grist-release <principal id> (Docker: docker compose exec privacyfence privacyfence-app --grist-release <principal id>).It prints Released the Grist connection of … The Grist API key PrivacyFence was given is deleted in Grist.
  3. In Grist, as an admin, check that person's API key is gone (or call /api/profile/user with the old key and get 401).
  4. Run the same release for the "Own key" person.It says the key was the person's own and stays; their key still works in Grist.
Report: ma5: managed key deleted, own key kept, or what differed.
