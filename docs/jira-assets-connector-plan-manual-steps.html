Jira Assets connector: your steps

The read-only Jira Assets connector is built by /implement on feature/jira-assets-connector. No phase needs anything from you. Everything below happens after the last phase merges and before the pull request does. Ticks are remembered in this browser.

Before implementation

Nothing. Run /implement on the plan straight away.

After implementation

ma1 · Add the Assets scopes to your Atlassian app

~10 min

Atlassian refuses the sign-in if PrivacyFence asks for a scope the app does not have. Do this for the app in your QA bundle and for the app in your real bundle.

  1. Open developer.atlassian.com → My apps and click the OAuth 2.0 app whose client id is in your QA org_config.json.
  2. Go to Permissions. Next to Jira API, click Configure, then Edit Scopes, then the Granular scopes tab.
    Type cmdb in the filter.
  3. Tick these four scopes and save: read:cmdb-schema:jira, read:cmdb-type:jira, read:cmdb-attribute:jira, read:cmdb-object:jira.
    Leave every write and delete cmdb scope unticked.
  4. Back on Permissions, find Jira Service Management API. Click Add (or Configure if it is already added), open Classic scopes, tick read:servicedesk-request and save.
    PrivacyFence needs this scope to find the site's Assets workspace id.
  5. Repeat steps 1–4 for the app behind your real (production) bundle, if it is a different app.

Done when both apps list the four read:cmdb-*:jira scopes and read:servicedesk-request under Permissions. The scope table is in docs/atlassian-setup.md, in its Jira Assets section.

ma2 · Seed the QA site's Assets workspace

~25 min

The live recording reads only these synthetic [QATEST] objects, never anything real.

  1. On the QA Atlassian site, open Assets from the Jira top bar. If Assets is missing, the site needs Jira Service Management with Assets; see What is Assets.
  2. Create an empty object schema named PrivacyFence QA [QATEST] with key PFQA.
  3. Add three object types: Account, Contract and Asset. Give Contract an Object attribute named Account that references Account. Give Asset an Object attribute named Contract that references Contract.
  4. Create 2 accounts, 2 contracts (each linked to an account) and 3 assets (each linked to a contract). Put [QATEST] in every name. Name one contract exactly PrivacyFence QA seed contract [QATEST].
  5. Open the issue PrivacyFence QA seed issue [QATEST] in the PFQA Jira project and link the seed contract to it with an Assets field, so the connected-tickets read has something to return.
  6. On the runner, add the assets: block to qa_environment.yaml, copied from tests/fixtures/qa_environment.yaml.example on the feature branch. Fill in seed_object_key (the seed contract's key, such as PFQA-12) if you know it.

Done when the PFQA schema shows 7 objects, and opening the seed contract shows its account and its linked Jira issue. The full checklist is in docs/connector-qa.md, under "Seed: Jira Assets".

ma3 · Re-grant the runner's Atlassian token with Assets

~15 min

The runner's current token was granted before the Assets scopes existed. Until it is re-granted, every live Assets call says “needs an extra Atlassian permission”.

  1. In a checkout of feature/jira-assets-connector, rebuild the QA bundle with the new flag. Add --atlassian-assets to the scripts/build_org_bundle.py command you used before. The client id and secret come from the same place as last time; never paste them into chat.
  2. Run .venv/bin/python scripts/qa_authenticate_connectors.py --org-config org_config.qa.json --only atlassian.
    Atlassian's consent screen now also lists Assets and Jira Service Management permissions. Pick the QA site.
  3. Copy the refreshed credentials/atlassian_token.json and the new bundle to the runner, as docs/connector-qa.md → Self-hosted runner describes. Keep mode 600.

Done when the token file on the runner has a "scopes" list that contains read:cmdb-object:jira.

ma4 · Hand back to the PR session for the live recording

~2 min of yours

Recording fixtures and running the live check are CI dispatches the PR session runs itself. They can only start once ma3 is done.

  1. Paste this into the session that is driving the pull request:
    ma3 is done: the runner's Atlassian token has the Assets scopes. Register check_assets in CONNECTOR_CHECKS and EXPECTED_FIXTURES, dispatch qa-record-fixture.yml with connector=assets against the PR branch, pull and review the fixtures, then dispatch connector-live-check.yml and link the run in the PR.
  2. Read the fixture diff the session points you to. It must hold only [QATEST] names, with no real tenant URL, account id or email.

Report back by ticking ma4 in the PR body, with the link to the green connector-live-check run.

ma5 · Try it on your real contracts

~10 min

Your real data is the only proof that the linked-object card is usable on a deep structure.

  1. Install a build from the PR branch. Open PrivacyFence Settings → Connectors, switch Jira Assets on, and click Authenticate…. Accept the extra Atlassian permissions.
  2. In Claude, ask: “Which account does contract <a real contract> belong to, and which assets are linked to it?”
  3. Check the approval card Read Linked Jira Assets Objects: one table per object type, an edges table, and nothing you did not expect. Approve it.
  4. Optional: on the next card, click Always allow → this schema. Ask again and confirm that no card appears.

Report back in the PR as one line: ma5: pass, or ma5: fail – <what was wrong>.
