# Plan: Jira extra fields and field lookup

## Goal

`jira_search_issues` returns a fixed set of fields (key, summary, status, issue type, priority,
assignee, reporter, labels, created, updated, url). Users want custom fields too, such as Story
Points, Sprint or Team, and built-in ones such as due date or fix versions. The agent does not know
a site's field ids (`customfield_10016`, or `cf[10016]` in JQL), so it also needs a way to turn the
names people use into ids.

After this change:

- **`jira_list_fields`** (auto-approved) lists the site's fields: name, id, custom or not, type, and
  the names JQL accepts for it. The agent finds "Story Points" there and learns it is
  `customfield_10016` and `cf[10016]` in JQL.
- **`jira_search_issues_with_fields`** (new, **reviewed**) runs a JQL search and adds the requested
  fields to each issue, by name, id or JQL id. The approval card shows a table of every issue and
  every requested value before anything is released.
- **`jira_get_issue`** takes the same optional `fields` parameter. The extra values are added to its
  existing review card.
- **`jira_search_issues`** keeps its shape and stays auto-approved. It now asks Jira for the fields
  it returns instead of `*all`.

Requested by the user in a planning session. There is no tracking issue.

## Design

### D1. Why a separate reviewed tool (the gate decision)

`jira_search_issues` is auto-approved because it returns metadata only; description and comments are
kept for the reviewed `jira_get_issue`. A custom field can hold anything (a multi-line "Acceptance
criteria" field, a customer name, a free-text "Root cause"). So extra fields go through a separate
tool with gate `review`, and the user sees every value before the agent does.

Rejected:

- **Extra fields on the auto-approved search.** Content would skip review, against the rule that
  only metadata runs without a card.
- **Auto, but refuse free-text field types.** Judging content by schema type is brittle: single-line
  text fields, labels and option values can carry content too, and an admin can add a field type
  the allowlist does not know.
- **One tool whose gate depends on its arguments.** A tool has exactly one gate in `TOOL_TO_GATE`.
  The tools reference, `privacyfence_check_policy` preflight and the gate invariants tests all rely
  on that.

The field list (`jira_list_fields`) is auto-approved: field names, ids and types are the site's
schema, not issue content.

The new operation `jira.search_issues_with_fields` has verb `Verb.SEARCH` and **no scope**: the
Jira scope catalogue in `src/privacyfence/policy/propose.py:332` lists `READ`, `CREATE`, `COMMENT`,
`UPDATE` and `TRANSITION`, not `SEARCH`, and a JQL query names no single project. So no standing
rule can auto-accept it and every call shows a card. Do not add it to the catalogue,
`resource_registry.py` or `scopes.py`.

`jira_get_issue` keeps operation `jira.read_issue` with or without `fields`; its existing project
rules still apply, because the issue's project does not change with the fields asked for.

### D2. Client: `src/privacyfence/jira_client.py`

New dataclass, after `JiraTransition`:

```python
@dataclass
class JiraField:
    id: str            # "customfield_10016", "duedate"
    name: str          # "Story Points", "Due date"
    custom: bool
    type: str          # schema type: "number", "option", "array of user", "" when Jira gives none
    jql_names: list[str] = field(default_factory=list)   # Jira's clauseNames, e.g. ["cf[10016]", "Story Points"]
```

New attribute on `JiraIssue`, next to `display_description`, with the same kind of comment:

```python
    # Not a dataclass field either: the requested extra fields, {Jira field name: simplified value},
    # set only by a search or get_issue that asked for them. None otherwise.
    extra_fields = None
```

New module constants, after `MAX_PAGES`:

```python
# The fields _parse_issue reads for a search result; description is left out on purpose.
SEARCH_FIELDS = ("summary", "status", "issuetype", "priority", "assignee", "reporter", "labels", "created", "updated")
# Keys a simplified field value never carries: links back into the API, avatars, and email addresses.
_DROPPED_VALUE_KEYS = frozenset({"self", "avatarUrls", "iconUrl", "emailAddress", "expand"})
_CF_JQL_RE = re.compile(r"cf\[(\d+)\]", re.IGNORECASE)
```

(`import re` is added at the top.)

New module function `simplify_field_value(value: Any) -> Any`, applied recursively. Checks in this
order:

1. `None`, `str`, `int`, `float`, `bool` → returned unchanged.
2. `list` → `[simplify_field_value(v) for v in value]`.
3. `dict` with `value.get("type") == "doc"` (rich text, ADF) → `JiraClient._extract_adf_text(value)`.
4. `dict` with `"accountId"` → `mask_emails(value.get("displayName") or "", value["accountId"]) or UNKNOWN_USER_LABEL`
   (a person is their display name, never an email or an id).
5. `dict` with `"value"` (select option) → `value["value"]`; when it also has a `"child"` dict with a
   `"value"` (cascading select), `f"{value['value']} > {value['child']['value']}"`.
6. `dict` with `"name"` (status, priority, version, component, sprint, group) → `value["name"]`.
7. `dict` with `"key"` (parent, linked issue) → `value["key"]`.
8. Any other `dict` → `{k: simplify_field_value(v) for k, v in value.items() if k not in _DROPPED_VALUE_KEYS}`.
9. Anything else → `str(value)`.

New `JiraClient` methods:

- `_all_fields(self) -> list[dict[str, Any]]`: the fetch-and-cache block now at the top of
  `_get_field_descriptor`, moved here unchanged (same `JiraClientError(f"failed to list Jira fields: {exc}")`).
  `_get_field_descriptor` calls it.
- `_get_field_descriptor`'s not-found message becomes
  `f"no Jira field named {field_name!r}; jira_list_fields lists the field names"`. The duplicate-name
  message gains `"; pass one of these ids instead"` at the end, replacing
  `"; rename one in Jira or ask your Jira admin to disambiguate them"`. Both errors reach
  `jira_update_issue` too, where the hint is equally right.
- `@staticmethod _to_jira_field(raw: dict[str, Any]) -> JiraField`: `id=raw.get("id", "")`,
  `name=raw.get("name", "")`, `custom=bool(raw.get("custom"))`, `type` from `raw["schema"]`:
  `schema["type"]`, or `f"array of {schema['items']}"` when type is `"array"` and `items` is set,
  `""` when there is no schema; `jql_names=list(raw.get("clauseNames") or [])`.
- `list_fields(self, query: str = "", custom_only: bool = False, max_results: int = 50) -> list[JiraField]`:
  clamp `max_results` to 1..200; keep fields whose name or id contains `query.strip().lower()`
  (case-insensitive; empty query keeps all); drop non-custom ones when `custom_only`; sort by
  `name.lower()` then `id`; truncate; log `"list_fields returned %d field(s)"`.
- `resolve_fields(self, refs: list[str]) -> list[JiraField]`, in order, deduplicated by id (first
  wins). Per ref, after `ref = ref.strip()`:
  - empty → `JiraClientError("field names must not be empty")`;
  - `_CF_JQL_RE.fullmatch(ref)` → id `f"customfield_{n}"`, looked up by id; not found →
    `JiraClientError(f"no Jira field with id {ref!r}; jira_list_fields lists the field names")`;
  - an entry in `_all_fields()` whose `id` equals `ref` exactly → that entry;
  - otherwise `_get_field_descriptor(ref)` (name match, with its errors).
- `@staticmethod extra_field_keys(wanted: list[JiraField]) -> list[str]`: each field's `name`,
  except that every field whose name is shared with another field in `wanted` (two fields with
  different ids but the same name, both asked for by id) is keyed `f"{f.name} ({f.id})"`.
- `_extra_fields(self, raw_fields: Mapping[str, Any], wanted: list[JiraField]) -> dict[str, Any]`:
  `{k: simplify_field_value(raw_fields.get(f.id)) for k, f in zip(self.extra_field_keys(wanted), wanted, strict=True)}`.

Changed `JiraClient` methods:

- `search_issues_page(self, jql, page_size=100, page_token=None, extra: list[JiraField] | None = None)`:
  pass `fields=[*SEARCH_FIELDS, *(f.id for f in extra or [] if f.id not in SEARCH_FIELDS)]` to
  `enhanced_jql`. After `_parse_issue`, when `extra` is not None set
  `issue.extra_fields = self._extra_fields(raw.get("fields") or {}, extra)` on each issue.
- `search_issues(self, jql, max_results=20, fields: list[str] | None = None)`: when `fields` is
  given, `extra = self.resolve_fields(fields)` before the first page (a resolution error is raised as
  is, not wrapped in `search_issues failed:`), and passed to every `search_issues_page` call.
- `get_issue(self, issue_key, fields: list[str] | None = None)`: when `fields` is given, resolve
  them before the API call and set `issue.extra_fields = self._extra_fields(raw.get("fields") or {}, extra)`.
  The API call itself is unchanged (`*all` already includes them). Every existing caller passes only
  the key and is unaffected.

### D3. Connector: `src/privacyfence/connectors/jira.py`

New constant and helpers, module level:

```python
MAX_EXTRA_FIELDS = 20
```

- `_parse_field_refs(value: str, tool: str, *, required: bool) -> list[str]`:
  - empty or whitespace `value` → `[]` when not `required`, else
    `ValueError(f"{tool}: fields must name at least one field; use jira_search_issues for the standard fields.")`;
  - `json.loads` fails, or the result is not a list of strings →
    `ValueError(f'{tool}: fields must be a JSON array of field names, e.g. ["Story Points", "Sprint"].')`;
  - an empty list → the same "at least one field" error when `required`, `[]` otherwise;
  - more than `MAX_EXTRA_FIELDS` → `ValueError(f"{tool}: fields can name at most {MAX_EXTRA_FIELDS} fields.")`.
- `_field_cell(value: Any) -> str`: `None` → `""`; `str` → itself; `list` →
  `", ".join(_field_cell(v) for v in value)`; `dict` → `json.dumps(value, ensure_ascii=False)`;
  anything else → `str(value)`.

**New tool `jira_list_fields`** (auto, `read_only=True`), placed after `jira_get_transitions`:

- Description: `"List the Jira site's fields, built-in and custom, with the id and JQL names behind
  each display name. Returns a list of {id, name, custom, type, jql_names}, sorted by name, at most
  max_results (default 50, capped at 200). Pass a name in the fields parameter of
  jira_search_issues_with_fields or jira_get_issue; in a JQL query use one of jql_names, e.g.
  cf[10016] > 3 or \"Story Points\" > 3. Auto-approved."`
- Params: `query` (`str`, not required, default `""`, `"Part of a field name or id, case-insensitive,
  e.g. 'story' or 'customfield_100'. Empty lists every field."`), `custom_only` (`bool`, not
  required, default `False`, `"True to list only custom fields. Default false lists built-in fields
  too."`), `max_results` (`int`, not required, default 50, `"Maximum number of fields to return.
  Default 50, capped at 200."`), `reason` (the standard required reason param).
- `_list_fields(self, query="", custom_only=False, max_results=50)`: fetch, `[asdict(f) for f in fields]`,
  `self._auto_audit("jira_list_fields", "List Jira Fields", "List fields", f"{len(fields)} field(s)", t0)`.
  The query text is not put in the audit summary.

**New tool `jira_search_issues_with_fields`** (review, `read_only=True`), placed after
`jira_search_issues`:

- Description: `"Search Jira issues using JQL and add extra fields to each one: custom fields such
  as Story Points or Sprint, or built-in ones such as due date or fix versions. Returns the list
  jira_search_issues returns, each issue with an added fields object mapping each requested
  field's Jira name to its value (people as display names, options and statuses as their names,
  rich text as plain text, an empty field as null), at most max_results (default 20, capped at
  100), in the order the JQL gives. Find field names with jira_list_fields. Use
  jira_search_issues instead when its standard fields are enough: it needs no approval. Requires
  user approval."`
- Params: `jql` (as `jira_search_issues`'s), `fields` (`str`, required: `"JSON array of the fields
  to add, by the name shown in Jira (case-insensitive), by id (customfield_10016, duedate) or by
  JQL id (cf[10016]), e.g. [\"Story Points\", \"Sprint\"]. 1 to 20 fields; jira_list_fields lists
  them."`), `max_results` (`int`, default 20, `"Maximum number of issues to return. Default 20,
  capped at 100."`), `reason`.
- `_search_issues_with_fields(self, jql: str, fields: str, max_results: int = 20)`:
  1. `refs = _parse_field_refs(fields, "jira_search_issues_with_fields", required=True)` before any
     API call; `max_results = max(1, min(max_results, 100))`.
  2. `wanted = await self._fetch(self._jira.resolve_fields, refs)`;
     `names = JiraClient.extra_field_keys(wanted)` (so the card names the fields even with no
     results).
  3. `issues = await self._fetch(self._jira.search_issues, jql, max_results, refs)` (the client
     resolves again from its cached field list).
  4. `result = [{**asdict(i), "fields": i.extra_fields or {}} for i in issues]`.
  5. `rows = [[i.key, i.summary, *(_field_cell((i.extra_fields or {}).get(n)) for n in names)] for i in issues]`.
  6. `gated_call(connector=self.name, tool="jira_search_issues_with_fields",
     tool_name="Search Jira Issues with Fields", summary=f"Search: {jql[:80]}", sender="Jira",
     raw_data=issues, filtered_data=result, gate="review",
     preview={"JQL": jql, "Fields": ", ".join(names)},
     new_info={"Results": str(len(issues)), "Field values": f"{', '.join(names)} for each issue"},
     details_text="\n".join(f"{r[0]} — {r[1]}: " + "; ".join(f"{n}: {c}" for n, c in zip(names, r[2:], strict=True)) for r in rows) or "(no matches)",
     pii_scan_text="\n".join(" ".join(r[2:]) for r in rows),
     preview_tables=[{"headers": ["Key", "Summary", *names], "rows": rows}] if issues else [],
     table_only=True, my_email=self.my_email, args={"jql": jql, "fields": fields})`
     and return its result.

**`jira_get_issue` gains `fields`**:

- New param after `issue_key`: `fields` (`str`, not required, default `""`, `"Optional JSON array
  of extra fields to return, as in jira_search_issues_with_fields, e.g. [\"Story Points\"]. Empty
  returns only the standard fields."`).
- Description: after the return shape, insert `"With fields, the issue also has a fields object
  mapping each requested field's Jira name to its value. "`.
- `_get_issue(self, issue_key: str, fields: str = "")`: `refs = _parse_field_refs(fields,
  "jira_get_issue", required=False)`; `issue = await self._fetch(self._jira.get_issue, issue_key, refs or None)`.
  When `refs`: `result["fields"] = issue.extra_fields or {}`;
  `new_info["Requested fields"] = ", ".join(issue.extra_fields or {})`; a block
  `{"type": "table", "caption": "Requested fields", "headers": ["Field", "Value"], "rows": [[n, _field_cell(v)] for n, v in (issue.extra_fields or {}).items()]}`
  goes after the Description text block and before the Comments table;
  `pii_scan_text` gains `"\n" + "\n".join(_field_cell(v) for v in (issue.extra_fields or {}).values())`;
  `args` becomes `{"issue_key": issue_key, "fields": fields}`. Without `fields`, everything stays
  exactly as today (same `args`, same blocks, same result keys).
- `call()` dispatches the two new tool names.

## Risks and open questions

- **Website count tests.** If `tests/unit/test_website_docs_pages.py` or
  `tests/integration/test_website_layout.py` count tools in a way the numbers in D5 do not satisfy,
  the worker trusts the tests' computed numbers (they come from `TOOL_TO_GATE`), uses those, and
  says so in the phase report.
- **A review tool with no scope.** If a test in `tests/unit/policy/` or
  `tests/unit/test_gate_real_evaluator.py` requires every operation-bearing tool to have a scope or
  a proposal, p2 stops with `status=blocked` and quotes the failing assertion; adding a scope is a
  product decision for the user.
- **Search result `fields` request.** If `enhanced_jql` with an explicit `fields` list leaves out a
  field `_parse_issue` reads in the live fixture test (`TestLiveFixtureParsing`), add that field to
  `SEARCH_FIELDS`, not `*all`.
- **`JiraIssue.extra_fields` on the class.** It is a class attribute (`None`) assigned per instance,
  like `display_description`; `asdict()` must not carry it. A test asserts that.
