ma1-qa-runner-groupPut the QA runner in an organization runner group that only main's two QA workflows can useabout 30 min

Today any pull request that adds a workflow can name the self-hosted runner, which holds live QA grants. A runner group restricted to selected workflows is GitHub's own guard.

  1. Open Organization settings → Actions → Runner groups and click New runner group.the new runner group form.
  2. Name it privacyfence-test. Repository access: Selected repositories → privacyfence/privacyfence. Tick Allow public repositories (the repository is public).one selected repository.
  3. Workflow access: Selected workflows, and add exactly these two:
    privacyfence/privacyfence/.github/workflows/connector-live-check.yml@refs/heads/main
privacyfence/privacyfence/.github/workflows/qa-record-fixture.yml@refs/heads/main
    Click Create group.the group listed with “Selected workflows”.
  4. On the runner host, as the runner's user, in the runner directory: sudo ./svc.sh stop, sudo ./svc.sh uninstall, then ./config.sh remove --token <token>, taking the removal token from the repository's runners page (the runner's … menu → Remove).the repository's runners page lists no runner.
  5. Get an organization registration token from Organization settings → Actions → Runners → New runner and register again, still non-ephemeral:
    ./config.sh --url https://github.com/privacyfence --token <token> \
  --runnergroup privacyfence-test --labels privacyfence-test --unattended
sudo ./svc.sh install <runner user>
sudo ./svc.sh start
    The token is short-lived and only for this command; do not store it anywhere.the runner Online in the organization's runner list, in group privacyfence-test; ~/privacyfence on the host is untouched.
  6. Check from a terminal with gh signed in as an org owner:
    gh api orgs/privacyfence/actions/runner-groups --jq '.runner_groups[] | select(.name=="privacyfence-test") | {restricted_to_workflows, selected_workflows, allows_public_repositories}'
gh api repos/privacyfence/privacyfence/actions/runners --jq '.total_count'
    restricted_to_workflows: true with the two refs above, and 0 repository-level runners.
  7. After the pull request merges, dispatch connector-live-check.yml on main from its Actions page.the run is picked up by the runner and its live-check job passes.

ma3-tag-rulesetAdd a ruleset that refuses v* tags from accounts without the repository admin roleabout 8 min

A pushed v* tag starts signing, publishing and PyPI. After this, only release.yml (through RELEASE_TAG_TOKEN) can create one.

  1. Open Repository settings → Rules → Rulesets → New tag ruleset.the new tag ruleset form.
  2. Name: release tags. Enforcement status: Active.Active selected.
  3. Bypass list: add the role Repository admin. The account whose fine-grained token is the RELEASE_TAG_TOKEN secret must be a repository admin; check that on Collaborators and teams.one bypass entry, Repository admin, “Always allow”.
  4. Target tags: Add target → Include by pattern → v*.v* under targets.
  5. Rules: tick Restrict creations, Restrict updates and Restrict deletions. Click Create.the ruleset listed as Active.
  6. Check: gh api repos/privacyfence/privacyfence/rulesets --jq '.[] | select(.target=="tag") | .name'release tags.
Report backPaste the gh api output into the pull request. The next real release goes through release.yml as usual; if its tag push is refused, the token's account is not an admin. An admin can still push a tag by hand; the docs say not to.

ma4-downloads-worker-environmentCreate the downloads-worker environment, limited to main, holding the two Cloudflare secretsabout 15 min

The Worker deploy job now names this environment; its branch rule is what stops a dispatch from another branch from deploying to downloads.privacyfence.eu. Do steps 1-3 before the pull request merges: the merge itself runs the deploy.

  1. Open Repository settings → Environments → New environment, name it downloads-worker, click Configure environment.the environment's settings page.
  2. Deployment branches and tags: Selected branches and tags → Add deployment branch or tag rule → branch main. Save.one rule, main.
  3. Under Environment secrets, add CF_DOWNLOADS_WORKER_API_TOKEN and CF_DOWNLOADS_WORKER_ACCOUNT_ID. GitHub never shows a stored secret again, so take the values from where you keep them, or create a new token at Cloudflare → API tokens with the same permissions as the current one (Workers Scripts edit and D1 edit on the account). Paste them only into GitHub's secret fields, never into a chat or a file.both names listed under Environment secrets.
  4. After the pull request merges: open deploy-download-worker.yml's runs and wait for the run on main (or dispatch it on main).the deploy job shows the downloads-worker environment and passes, including its /health smoke test.
  5. Then delete the repository-level copies of the two secrets at Repository settings → Secrets and variables → Actions.the two names gone from repository secrets, still present on the environment.

  1. On an Ubuntu 24.04 desktop VM, download the .deb artifact from the build.yml run linked in the pull request (Actions → the run → Artifacts) and install it: sudo apt install ./privacyfence_*_amd64.deb. Install on Linux has the details.the companion's tray icon after you log in again.
