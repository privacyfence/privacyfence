Inbox Triage Setup

Steps only you can do for the inbox-triage changes: two before /implement starts, then the rollout after the release ships. Secrets never go into chat, the repo or this page: each step says where one is stored.

0 of 0 steps

Before implementation

Do both, then run /implement. The second one tells you early whether the scheduled task can hold a scoped token at all.

1. Turn scoped tokens on for the organization install

about 10 min

Organization mode keeps scoped tokens off until an administrator enables them. Without it there is no Scoped tokens section in Settings, so neither step 2 nor the rollout can start. A scoped token needs no --enable-unattended-sessions: it starts an unattended session without that opt-in.

  1. Flag reference: the --enable-scoped-tokens row in the organization setup guide, and scoped_tokens.enabled in the configuration reference.
  2. Keep every other flag as it is.
  3. In Settings this is Install/Update Organization Config… for a desktop install, or your usual deploy for a server.
  4. You should see a New token form and an empty token list.

Done when: Settings shows the Scoped tokens section with a New token form.

2. Prove the scheduled task can connect with a scoped token

about 20 min

A scoped token is a bearer credential for /mcp. The repository cannot tell whether a Cowork scheduled task can present one, and request 2 depends on it. Test with a throwaway token that can do almost nothing, so a failure costs nothing.

  1. That tool needs no rule, so it is not in the main tool list. With no rule ticked, open the collapsed Tools that need no rule, from other connectors section under Tools and tick it there. If your version has no such section, tick any Gmail rule, tick the tool when it appears, then untick the rule before creating; tell Claude if neither works. Leave the personal-data box unticked. Confirm with your passkey if asked.
  2. Local mode puts it on your clipboard; organization mode shows it in a dialog with a Copy button.
  3. In a Claude Code environment this is the environment's secrets setting (cloud environment docs). Name it PRIVACYFENCE_TRIAGE_TOKEN.
  4. With Claude Code that is: 
    claude mcp add --transport http privacyfence-triage https://<your-host>/mcp --header "Authorization: Bearer $PRIVACYFENCE_TRIAGE_TOKEN"
    For Cowork, check whether a connector or plugin setting accepts a bearer or API-key header. Setup reference: Scoped tokens.
  5. The status answer shows the token's expiry.
If Cowork cannot present a bearer token, stop here and tell Claude before running /implement. The server changes still help, but the token has to come from another runner: a Claude Code scheduled task, or privacyfence-sync.

Done when: a scheduled run listed exactly one connector tool and showed the token's expiry. Or you have told Claude it could not connect.

After the release ships

Rollout on your own install once a release with these changes is installed. Not part of /implement and does not block the pull request.

Create the inbox-triage rules and token

about 25 min

Order matters: a token keeps only the operations a rule had when the token was created. Edit the rules first, then create the token. A token made earlier never gains the new move verb.

  1. Each rule then reads: Gmail - label …: allow update, move.
  2. The whole value is one query; commas stay inside it. A thread is readable only when every message in it matches.
  3. Neither takes a value.
  4. Leave out the task lists, Drive and every other Grist or Peek rule. That is what keeps a hostile message from reaching them.
  5. Tick Let exports, downloads and page uploads carry personal data too only if the dashboard page can hold personal data.
  7. Settings → Audit log, or the weekly file under the audit folder.

Report back: one line for each result, for example "label then archive passed; body read passed; no denials", or the first denied tool.

Checkboxes are remembered in this browser only.
