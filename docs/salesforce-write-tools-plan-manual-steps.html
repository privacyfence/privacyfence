PrivacyFence · Salesforce write tools

Hands-on checks for the Salesforce write tools

These are the steps that only you can do. CI tests the cards with a stand-in for the approval window, and the live lifecycle check runs on the QA runner. What is left is looking at the real cards against a real org.

Before implementation

Nothing. You can run /implement straight away.

After implementation, before the PR merges

1. Check a single-record update card and a batch create card against a real Salesforce sandbox

Takes about 20 minutesNeeds a Salesforce sandbox or developer org, not production
  1. Check out the PR's branch feature/salesforce-write-tools on your development machine and start the daemon with ./scripts/dev_start.sh. See dev-vs-live-setup.md. A source run will not start on a machine that has the packaged app installed.
  2. In PrivacyFence Settings, make sure Salesforce is signed in to the sandbox. If it is not, use Authenticate… on the Salesforce row. See salesforce-setup.md. You do not need to sign in again: the existing api scope already allows writes.
  3. In an AI client connected to this daemon (Claude Desktop or Claude Code), ask: "Find a test Account with salesforce_search, then use salesforce_update_record to set its Description to 'PF write test' and its Industry to 'Retail'." Approve the search card. You should see an approval card titled Update Salesforce Record, with the record's name, Fields changed: 2, an Effect line that mentions your org's own automation, and a Field | Current | New table.
  4. Look at the card's Always allow offer, but do not accept it. It should offer this object type for Account, and its verbs should include update.
  5. Approve the card. Open the Account in Salesforce. Description and Industry have their new values. No other field changed.
  6. Ask for the same update again. No card appears. The assistant gets an error saying every field already has the value given.
  7. Ask: "Use salesforce_create_records to create two Contacts on that Account: LastName 'PF test A' and LastName 'PF test B'." Deny the card. The card is titled Create Salesforce Records, shows Records: 2, and has a table with a # column. After you deny it, no Contact exists in Salesforce.
  8. Ask again and approve this time. Check in Salesforce that both Contacts exist on the Account, then delete them by hand. PrivacyFence has no delete.
  9. Open the audit log in Settings. There are entries for the update, the denied create and the approved create. None of them shows field values.
Report back: tick the PR's ma1-real-cards item, and paste one line into the PR: 
ma1-real-cards: PASS (update card, no-op refusal, batch create deny+approve, audit) — org: sandbox
If any step failed, write FAIL, the step number and what you saw.
